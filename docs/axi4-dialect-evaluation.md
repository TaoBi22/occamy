# Evaluating the CIRCT AXI4 dialect on Occamy

*Draft. Verified in VCS: every stage is cycle-identical to the handwritten crossbars, in both configs.*

We replaced Occamy's handwritten `axi_xbar` instances with crossbars generated by the CIRCT AXI4 dialect (`axi4-working-branch` of `TaoBi22/circt`, at `2d0644558` or later). The generated crossbars connect straight to Occamy's existing structs, with no glue logic. Every full-AXI crossbar is now generated except the interleaved HBM crossbar, which stays handwritten by design. This page records what worked, what we had to work around, and what we found along the way.

## How it is wired

1. **Description.**
   - `AxiXbar.emit_axi4_dummies()` in `util/solder/solder.py` turns each selected solder crossbar into an `axi4.dummies` description, built from the address map and connectivity solder already computes.
   - Nothing is transcribed by hand, so the description follows the chosen configuration automatically.
   - Selection is the `AXI4_XBARS` Makefile variable, which defaults to all the generated crossbars above. `AXI4_XBARS=` gives the all-handwritten flow.
   - Where solder's address map is symbolic, occamygen supplies the same rules as constants computed in Python. `soc_narrow_xbar`'s quadrant windows are elaboration constants. The quadrant and ctrl crossbars' maps depend on the tile, so those get one map per tile (G4).
   - Crossbars with atomics mark every endpoint `pulp.atops`, as `axi_xbar` carries `atop` on every port. The atomics filters Occamy already has downstream stay where they are, so no `pulp.atop_filter` is used.
   - `ATOPs` and `Connectivity` are not passed through `PULP_CONFIG`; the dialect derives both. The only settings passed through are `LatencyMode`, `MaxSlv/MstTrans` and `FallThrough`.
   - Solder refuses a crossbar it can't describe faithfully: one with an interleaved mode, or with a symbolic address map but no constant stand-in.
2. **Lowering.** `util/occamygen/axi4_lower.py` groups the crossbars by user width.
   - Each group gets one run of `--lower-axi4-dummies-to-axi[=user-width=N] --lower-axi4-to-hw='pulp-mapping=true req-resp-ports=true'`, then `--lower-seq-to-sv --export-split-verilog`.
   - The results are concatenated into `target/sim/src/occamy_axi4_xbars.sv`.
3. **Instantiation.** solder instantiates the generated module where `axi_xbar` used to be. It connects the elements of the existing `<xbar>_in/out_req/rsp` arrays, and everything else in the templates stays as it was.
   - Per-tile crossbars are selected with `case (TileId)`. `TileId` is a new parameter of `occamy_quadrant_s1` and `occamy_quadrant_s1_ctrl`.
4. **Checks.**
   - The lowering script compares every generated port's bit width, and the wrapper's manager and subordinate numbering, with what solder connects.
   - It fails on any mismatch, on any inserted converter, and on two user-width groups producing the same wrapper name.
   - `ASSERT_INIT`s check Occamy's struct widths against the same numbers, and an `ASSERT` checks that `tile_id_i == TileId`.
5. **Machines without CIRCT.** `AXI4_XBARS_SV=<file>` uses a file lowered on another machine. The file carries a sha256 of the description it was lowered from, so a stale file is rejected.

**Size (full config):**
- **Description:** 1,313 lines of MLIR: 33 modules, 100 managers, 122 subordinates and 716 `accesses` ops.
- **Output:** about 27,000 lines of SV in 61 modules.
- **Generator and template changes:** about 300 lines, plus the 150-line lowering script.

**Dummies subdialect or core dialect?** We stayed with the dummies subdialect.
- **What the core dialect would remove:** F4 and G9. It states ID widths, user widths and port order explicitly.
- **Why it isn't needed:** none of those issues block a crossbar, and user width is handled by one lowering run per width.
- **What that says about the dummies layer:** its inference (ID sizing from outstanding counts, window propagation) is built for deriving an interconnect. In a drop-in, where every width is already fixed, it gets in the way more than it helps.

## Verification

**Done locally, for both configs, on all 33 generated crossbars:**
- **Address decoding.** At every rule boundary, the generated `AddrMap` picks the same output as the handwritten map with its default port 0.
  - Symbolic handwritten rules were evaluated from the baseline RTL's own expressions and `occamy_pkg` constants: `s1_quadrant_base_addr`, `cluster_base_addr` per tile, and `internal_xbar_base_addr` per tile.
- **Configuration.** These match the handwritten crossbars:
  - `Connectivity`, now derived by the dialect, compared as sets of connected (manager, subordinate) pairs;
  - `ATOPs`, now derived from the `pulp.atops` markers;
  - `MaxSlv/MstTrans`, `FallThrough` and `LatencyMode`, including the ctrl crossbars' `CUT_SLV_PORTS` and `CUT_MST_PORTS`.
- **Atomics and user bits.** In the narrow wrappers, `atop` is wired from every manager into `axi_xbar` and on to every subordinate, and `user` is carried at 5 bits. Nothing is tied off, and no filters are inserted.
- **Ports.** Widths and order checks pass, and no converters are inserted.
- **RTL diff.** The generated SoC, quadrant and ctrl RTL changes only where intended: addrmap wires removed, instances replaced, and the `TileId` parameters added. `occamy_pkg.sv` is unchanged. With `AXI4_XBARS=`, the only difference from the baseline is the unused `TileId` parameters.
- **Elaboration.** Verilator `--lint-only` raises no errors, and no warnings on the crossbar instances or the generated file:
  - `occamy_soc`, single-cluster config;
  - `occamy_quadrant_s1`, including its ctrl, in the full config with `TileId` 0 and 5.

**VCS regression: cycle-identical to the handwritten crossbars.** Three stages were each compared against the handwritten version, for `sw/run-full-occamy.yaml` and `sw/run-single-cluster.yaml`:

- the networks contain only crossbars, with no adaptors or CDCs to fuse;
- every crossbar output is addressable by some manager, because output 0 receives all unmapped ranges;
- `hbm_xbar` stays outside the network.

## What went smoothly

- **Port layout.** `req-resp-ports=true` produces PULP's exact struct layout, so the generated ports connect directly to Occamy's `axi_a48_d*_i*_u*_req_t`/`_resp_t`.
- **ID widths.** Setting `outstanding = 2**iw` on each endpoint reproduces Occamy's ID widths exactly, including `clog2(#inputs)` added downstream. No `axi_iw_converter` is inserted.
- **Derived settings.** `Connectivity`, derived from the `accesses` ops, and `ATOPs`, derived from the atomics markers, both match the handwritten values on every crossbar.
- **Wrapper sharing and naming.** Identical crossbars share one PULP wrapper. Wrappers that differ only in address map get unique names (`_0`, `_1`, …).
- **Top of the address space.** Windows that run to the end of the address space lower to `end_addr = '0`. That is correct, because PULP's `addr_decode_dync` treats it as "to the end".

## Issues found

- **F1: Connectivity was passed in the wrapper's port order (fixed upstream).**
  - `PULP_CONFIG_Connectivity` used to be the only way to set connectivity, and it was copied verbatim. But the wrapper numbers downstream ports in MLIR use-list order, the reverse of creation order. For `soc_wide_xbar` this silently put the no-loopback zeros on the wrong manager/subordinate pairs.
  - The dialect now derives `Connectivity` from the `accesses` ops (`6f1b8edb1`).
  - Solder still emits subordinates in reverse, so the wrapper's numbering matches solder's and the generated RTL can be compared index by index with the handwritten crossbar.
- **F2: No output describing the generated ports.** To check widths and order, the script lowers in two stages and parses the port types and `hw.struct_explode`/instance wiring out of the HW-level MLIR. A small JSON manifest from `--lower-axi4-to-hw` would replace that. It would list each module's ports with bit widths and the PULP index for each named port.
- **F3: Source locators.** The exported SV contains absolute paths of the input MLIR. Turning them off needs `--test-apply-lowering-options=options=locationInfoStyle=none`, a test pass, because `circt-opt` has no `--lowering-options`.
- **F4: The `accesses` ops are verbose.** Each window of each reachable subordinate needs its own `accesses` op: 716 for the full config. A form like "manager reaches all of subordinate X's windows" would shrink that considerably.
- **F5: Typedefs at file scope.** Each PULP wrapper declares its typedefs outside the module, in `$unit`. The names are prefixed, so we saw no clash. They still add to a shared namespace when the file is concatenated into a larger compilation unit.
- **F6: `ATOPs` defaulted to `1'b1` (fixed upstream).** The PULP mapping claimed atomics support the wrapper couldn't provide. It now defaults to off (`472d889d4`) and is derived from the markers.
- **F7: Wrapper names don't encode user width.** Two crossbars of the same shape but different user widths would generate the same PULP wrapper name with different contents. Separate lowering runs make this visible; the lowering script stops rather than silently keeping one. It doesn't occur in Occamy, because the u0 and u5 crossbars differ in data width.

## Gaps

### G1: user signals (resolved)

`--lower-axi4-dummies-to-axi=user-width=N` (`40fde9494`) applies one width to every port in a network. Occamy's crossbars each use a single user width, so the flow lowers each width separately. Per-endpoint user width would only be needed for a single network that mixes widths.

### G2: atomics (resolved in the PULP lowering)

`atop` is an AXI5 feature that PULP's library ports back into AXI4 ("AXI4+ATOPs from AXI5"). It doesn't belong in an implementation-neutral AXI4 dialect, so the dialect stays AXI4 and the PULP lowering handles it.
- **The markers:** `pulp.atops` marks endpoints that issue or accept atomics, and `pulp.atop_filter` marks subordinates that need atomics filtered out in front of them. They sit on `ext_manager`/`ext_subordinate`, and the dummies lowering moves them onto module ports, which network rewrites leave alone.
- **What the PULP lowering does:**
  - carries `atop` along the marked paths, including through `req-resp-ports` struct ports;
  - sets `ATOPs`/`AtopSupport` on exactly the components those paths cross;
  - inserts filters where marked;
  - rejects paths PULP can't carry, e.g. through `axi_burst_splitter`.
- **Caveat:** passes above the PULP lowering still count atomics as plain writes.

### G3: default port (emulated)

Every Occamy crossbar routes unmapped addresses to output 0. The dialect has no default port, so output 0 gets every range not covered by another rule. This reproduces the routing exactly wherever the address map is static, which it now is for every generated crossbar. A native default subordinate on `xbar` would make the emulation unnecessary, and it would be needed for any design whose maps really are computed at run time.

### G4: address maps computed at run time (fixed on the Occamy side)

The quadrant and ctrl crossbars compute their address maps from `tile_id_i`:
- cluster bases in `occamy_quadrant_s1.sv.tpl:58`;
- the ctrl `internal` window in `occamy_quadrant_s1_ctrl.sv.tpl:71`.

One shared module serves all 6 quadrants. `tile_id_i` is a literal at every instance, though, so each map is really fixed per instance.

**Fix:**
- `occamy_quadrant_s1` and `occamy_quadrant_s1_ctrl` have a `TileId` parameter. The SoC passes the same literal it already drives on `tile_id_i`, and the quadrant forwards it to its ctrl.
- Solder generates one crossbar per tile, from constant per-tile address maps computed in Python.
- Each module picks its crossbar with `case (TileId)` in a generate block. An `ASSERT` checks that `tile_id_i == TileId`.
- The shared typedefs and signal arrays are unchanged, so the adapter chains in the templates are untouched.

**Dialect alternatives (not pursued):**
- windows relative to a base input, which PULP can lower onto `addr_map_i`;
- windows expressed in terms of a module parameter.

Both would need the dialect's static checks (overlap, coverage, working out each manager's windows) to reason about an unknown offset.

### G5: interleaved HBM crossbar (stays on the RTL side, by design)

`hbm_xbar` is an `axi_interleaved_xbar` whose only subordinates are the 8 HBM channels. When the `INTERLEAVED_ENA` register bit is set, it stops routing by range:
- **Routing:** it picks the channel from address bits `[18:16]`, spreading consecutive 64 KiB blocks over the 8 channels.
- **Address compaction:** it strips those bits from the forwarded address (`axi_interleaved_xbar.sv:96-117`).

**Decision:** this is handled on the RTL side of the AXI-to-RTL bridge, not in the dialect. The dialect network ends at `hbm_xbar`'s ports; it already appears only as the `out_hbm_xbar` subordinate of the generated pre-xbars and `soc_wide_xbar`. Three things make it a poor fit for the dialect:
- **Enumerating the interleaved windows doesn't scale.** Listing each channel's granules as contiguous windows would take 163,840 windows over Occamy's 10 GiB of HBM space. PULP's range decoder would turn that into about 2.3 million 48-bit comparators, for what three address bits do today.
- **Address compaction is address rewriting.** No window description expresses it.
- **The mode switch while running is a configurable-interconnect feature, not an AXI one.**

**If non-contiguous decoding is needed elsewhere:** the implementation-neutral form would be masked windows, matching `(addr & mask) == value`. Two per channel would describe Occamy's interleaving, and `common_cells`' `addr_decode_dync` already supports arbitrary masks through its `Napot` mode. That covers only the routing, though, not compaction or the mode switch.

**Test coverage:** no regression test enables interleaving, because nothing calls `activate_interleaved_mode_hbm()`. A plain generated crossbar would pass the tests but silently lose the feature, which is another reason not to replace it. (Separately, `deactivate_interleaved_mode_hbm()` in `sw/host/runtime/host.c` writes `1`, not `0`.)

### Not blocking, but worth fixing

- **G7: adapters with no dialect op.** `axi_riscv_atomics`, `axi_atop_filter`, `axi_isolate`, `axi_tlb_noreg`, the RO cache, `axi_modify_address`, user-width changes and `axi_multicut` stage counts have no op, and the dummies level has no cut or CDC. This prevents describing the whole network as one dialect network instead of crossbar by crossbar.
- **G8: `test_i` is tied to `1'b0` inside the wrapper.** Occamy drives it from `test_mode_i`. It should be exposed as a port.
- **G9: `outstanding` sets three things at once:** the ID width, the default `MaxSlv/MstTrans`, and the bottleneck warnings. Occamy wants e.g. 4-bit IDs with 64 transactions, so `MaxTrans` is forced through `PULP_CONFIG`.
